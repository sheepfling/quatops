# CAP-300: canonical interoperability validation

CAP-300 asks whether a converter preserves a physical rotation across explicit
coordinate frames. It separates algebra, coefficient storage, frame mapping,
and each native target boundary. A target name never supplies a forward axis,
an asset model axis, or an active/passive interpretation.

## Canonical boundary

The canonical value is a unit, active Hamilton quaternion in WXYZ order,
acting on column vectors in an explicit right-handed source frame. Callers
provide the source and destination world/body maps. For a shared orthogonal
basis map `B`, `R_target = B R_source Bᵀ` and
`q_target.xyz = det(B) B q_source.xyz`. For different maps,
`R_target = B_world R_source B_bodyᵀ`; a quaternion result requires equal
determinant parity. Angle units apply when constructing or inspecting a
quaternion, not to its four coefficients.

## What the proof checks

Each captured target output includes native coefficients and the native images
of +X, +Y, +Z. Repository replay checks establish:

- canonical-to-native and native-to-canonical coefficient conversion;
- physical action equivalence, `B (R_source p) = R_native (B p)`;
- both orders of a noncommuting mixed rotation product;
- inverse conversion and explicit source/destination frame declarations.

The pinned engine or library supplies the stored native actions. SciPy supplies
an independent formula check and is reported separately from target-runtime
execution. Shared property checks generate all 48 signed-axis maps in memory,
including reflected maps, inverse conversion, noncommuting composition, and
distinct world/body corrections; passing generated outputs are not retained.

Capture producers are inspected separately: they must not import or call
QuatOps, and native vector actions must come directly from the target API.
Frozen values and source/build hashes live in the versioned oracle packages.

## Direct engine pair capture

The Unity 6000.5.2f1 to Godot 4.7 transfer is an optional direct pair witness
from the initial cross-engine investigation. It is kept as a separate named
case because it is the only pairwise native capture in this branch; it is not
why those converters are grouped, and it is not required to accept either
single-target adapter. Its frame map is explicitly declared in the fixture.
No other pairwise transfer is claimed.
