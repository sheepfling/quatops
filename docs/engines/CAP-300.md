# CAP-300: canonical interoperability validation

CAP-300 moves engine verification from “does this API implement quaternion
math as expected?” to “does this converter preserve a physical orientation
across the declared frames?” Engine math captures remain useful inputs, but a
target is converter-validated only when its adapter passes the native action
checks below.

## Canonical interchange value

CAP-300 uses this explicit QuatOps boundary contract:

| Property | Contract |
| --- | --- |
| Algebra | Hamilton |
| Coefficient order | WXYZ |
| Rotation action | Active, `q (0, v) q*` |
| Matrix action | Column vectors |
| Coordinate frame | Right-handed |
| Construction units | Radians |
| Normalization | Unit quaternion at this boundary |
| Frame metadata | Source and destination world/body frames are explicit |

The radians entry applies to angles used to construct or inspect a quaternion;
four quaternion coefficients do not themselves have angle units. The canonical
interchange value does not add frame names to a bare four-number tuple, so a
caller must carry its frame mapping alongside it.

The scalar-first Hamilton representation in `quatops.python.hamilton` is a
natural storage choice for this contract. The rest of QuatOps continues to
expose Hamilton/JPL and WXYZ/XYZW modules; adapters must say which representation
they accept and return.
`SignedAxisMap.map_hamilton_wxyz` is a convenience that composes storage order
and a shared frame map. Callers can reorder through the explicit Hamilton/JPL
module functions and use `map_hamilton_xyzw` to exercise the layers separately;
the 48-map oracle asserts both routes agree.

## Independent conversion layers

1. **Algebra** changes Hamilton/JPL interpretation. Keep conjugation/sign rules
   separate from coordinate handedness.
2. **Storage** reorders WXYZ and XYZW. Reordering alone preserves the same
   coefficient values and does not convert algebra or frames.
3. **Frames** map vector coordinates. `SignedAxisMap` expresses signed-axis
   mappings and can be inverted; `change_rotation_basis` handles separate
   world and body maps as `B_world R B_body.T`.
4. **Target boundary** encodes native coefficient storage. The named pure-Python
   modules `quatops.engines.unreal`, `.unity`, `.godot`, and `.blender` each
   require an explicit, precompiled `QuaternionFrameMap`; no engine name
   supplies default world or model-forward axes. Unreal, Unity, and Godot use
   XYZW storage, while Blender uses WXYZ.

For one shared orthogonal basis map `B`, the active Hamilton conversion is
`R_target = B R_source B.T` and
`q_target.xyz = det(B) B q_source.xyz`. Different world/body maps use the
two-sided matrix formula. Its result is representable by a unit quaternion only
when the two maps have equal determinant, so the result matrix has determinant
`+1`.

The Unity-to-Godot example in the shared fixture declares Unity `+Z` as forward
and Godot `-Z` as forward, with matching `+X` right and `+Y` up. For those named
frames only, `B = diag(1, 1, -1)` and Unity XYZW coefficients map to Godot as
`(-x, -y, z, w)`. Copying Euler parameter values between APIs is a different
operation from preserving a physical orientation through this frame map.

## Converter acceptance checks

Each native target fixture consumes the fixed WXYZ inputs in
[`canonical_inputs.json`](../../experiments/interoperability/v1/canonical_inputs.json)
by case ID and records the target API's coefficient result and direct action on
all three basis vectors. One asymmetric mixed-vector action is retained for the
`mixed_a` orientation per precision profile. Repository acceptance tests route
coefficient conversion through the corresponding named adapter. Tests then establish:

- canonical-to-native coefficients from QuatOps, including storage order;
- native-to-canonical conversion of captured target coefficients, checked
  against each engine's basis actions and physical-vector results;
- `B (R_canonical p) == R_native (B p)` for the retained `mixed_a` witness;
- both orders of a noncommuting product, with native coefficient and basis
  actions;
- Unity-to-Godot coefficient transfer for the selected orientations and one
  native mixed-vector action across the two pinned runtimes.

SciPy builds the independent expected source matrices. It is formula evidence;
the captured right-hand vector and basis actions are the engine-runtime
evidence. They are deliberately reported separately.

### Fixture independence audit

The CAP-300 capture programs do not import or call QuatOps. They use literal,
fixture-local coefficient and vector maps for the explicitly declared frame
maps, then call the pinned engine's quaternion-vector action to emit native
rotated basis vectors and one mixed-vector result. Canonical input coefficients
are referenced by case ID from the hashed shared input file; repeated copies
are omitted from the retained target files. This means the captured
quaternion coefficients by themselves are not an independent proof of the
conversion formula: the conversion equation is duplicated in the capture
producer. The independently useful runtime oracle is the engine-produced
physical action, which the replay tests compare against the separately built
SciPy source matrix and declared basis map. Reverse conversion starts from the
captured target coefficient values and checks the inverse against the
independently declared canonical input and physical action. Treat coefficient
equality as a consistency check and native vector action as the primary
conversion proof.

The SciPy suite now additionally checks noncommuting composition through each
named adapter for every one of the 48 signed-axis maps, including reflected
maps. It compares native quaternion composition and an arbitrary vector action
with the independently mapped source result. For separate world and body maps,
the frame-map tests cover every equal-parity pair, including identity source
orientation: distinct maps can correctly turn source identity into a fixed
nonidentity destination correction. Composition is a homomorphism only for a
shared coordinate map (or compatible typed intermediate frames); do not apply
the shared-map product law blindly to unrelated world/body frame pairs.

| Godot 4.8-dev1 `Quaternion` | Pass | Pass | Pass; development snapshot | No additional pair captured |

| Unity 6000.5.2f1 → Godot 4.7 stable | — | — | Both native captures match after the explicit `diag(1,1,-1)` map | Pass |

Each pass is based on the runtime project executing and emitting the
canonical-interoperability section, followed by the repository replay check in
[`test_canonical_interoperability.py`](../../tests/quatops/engines/test_canonical_interoperability.py).
That test reads frozen outputs and does not launch an engine. Blender's identity
probe frame does not establish a universal Blender world axis or an imported
asset's local forward direction.

The selected, lossless native witnesses are stored under
[`tests/oracles`](../../tests/oracles/). Each target/version has a compact
`contract.json` and `witnesses.json`; the latter preserves eight canonical
orientations and both captured native product orders. The capture exporter,
original full-capture hash, exporter hash,
runtime build record, and shared-input hash are recorded for provenance. Full
successful discovery sweeps are generated to temporary paths and are not
committed as goldens. Pytest reads the selected frozen values after native
processes exit. The SciPy adapter oracle also calls all four named boundaries
for every one of the 48 signed-axis maps; that generated formula check is
separate from the pinned-runtime action captures.

The per-target quaternion converter gate does not require every pairwise
engine transfer. Only Unity 6000.5.2f1 → Godot 4.7 stable has a separate
direct native pair proof; other pairwise transfers are not claimed here.

## Remaining scope

This milestone validates the named storage/frame adapters against the listed
native APIs while requiring callers to choose and inspect each frame map. Asset
import, mesh model-forward correction, transform scale/decomposition beyond
the captured witnesses, and animation interpolation remain separate acceptance
rows. The auxiliary Cesium, glTF,
OpenUSD, and ROS proofs cover only the placement, static scene, and named-frame
operations listed above; they do not establish behavior for untested loader
routes or general asset pipelines. Other native math and transport captures
are not converter validation until they record the relevant conversion
directions and native physical-vector actions.
